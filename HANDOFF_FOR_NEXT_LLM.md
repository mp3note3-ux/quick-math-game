# AI Handoff: Combination Game

## 1. Project identity

- Repository: https://github.com/mp3note3-ux/quick-math-game

- Default branch: `main`

- Frontend tooling: Vite 6, React 19, TypeScript (strict), CSS
- Test tooling: Vitest (unit/integration/simulation), Playwright (browser e2e)
- Node requirement: Node.js 20 or later

- Additional UI language: Korean

This document is written in English. The codebase contains Korean translation values in its Korean locale catalog; do not remove that locale unless the project owner explicitly changes the language requirement.

## 2. Project goal

Build an independent implementation of a three-attribute combination card game (반짝 ✨ 결! 합! style). The intended longer-term product includes multiplayer rooms, host/student roles, synchronized state, rankings and history. **Stage 1 (solo revamp + foundations) is what exists now. Stage 2 (multiplayer/backend) is deferred until the owner explicitly authorizes it.** Read `GAME_DESIGN_IMPROVEMENT.md` for the full product brief and `CLAUDE.md` for working rules.

## 4. Key design decisions (Stage 1)

- **Domain purity**: `src/domain/` never imports React, DOM, storage, or network. The React layer wraps the pure session reducer with `useReducer`; simulations drive the same reducer directly, so simulated scoring is exactly the game's scoring.
- **Configurable scoring**: all values live in `ScoringConfig` (`src/domain/scoring.ts`). Defaults reproduce the prototype (+1 flat, −1 wrong, +3 correct "no sets left"). Final values are an OPEN owner decision — run `npm run simulate` and review `docs/scoring-simulation.md` before changing `DEFAULT_SCORING_CONFIG`.
- **Difficulty levels**: `combinationLevel()` = number of all-different attributes (1–3). This is the design brief's hypothesis; simulations compare [1,1,1] vs [1,2,3] vs [1,2,4].
- **Fairness guards**: duplicates never score; idle scores exactly 0; `isEligibleForRanking()` requires ≥1 verified set; sessions with none show an "unranked" note. Simulation tests assert engaged play beats inactivity.
- **Feedback**: typed outcomes, never pre-baked strings. Wrong picks carry `explainInvalid()` output ("Shape color has two alike and one different"). All point text is rendered from config values.
- **Persistence**: `StoredProfile` (schemaVersion 1) in localStorage via a typed `StorageRepository`. Missing/malformed/outdated/blocked storage falls back to defaults and never throws. The Stage-0 key `combination-game-player-name` is migrated into the profile on first run. The locale key `combination-game-language` is managed by the i18n module. Progress is browser-local only — the UI says so.
- **Deterministic boards**: `?seed=<int>` makes the session use a seeded RNG and exposes `window.__COMBINATION_GAME__.getState()` for tests. Normal play uses `Math.random`.
- **Locale catalogs were once swapped** (en.json held Korean). Fixed; `locales.test.ts` guards the regression and asserts EN/KO key + placeholder parity. Type-checked: `const koCatalog: Catalog = ko` fails the build on missing keys.

## 5. Commands

```bash
npm install
npm run dev         # Vite dev server (usually http://localhost:5173/)
npm test            # Vitest: domain, storage, i18n, simulation guards
npm run build       # tsc --noEmit + vite build
npm run simulate    # regenerate docs/scoring-simulation.md (tsx)
npm run test:e2e    # Playwright; first time: npx playwright install chromium
```

CI (`.github/workflows/ci.yml`): Node 20 → `npm ci` → `npm test` → `npm run build` → Playwright chromium install → `npm run test:e2e`.

## 7. What is NOT finished

### Open owner decisions (evidence first — see docs/scoring-simulation.md)
- Final per-level rewards ([1,1,1] vs [1,2,3] vs [1,2,4]).
- Whether to floor the match score at 0.
- The correct "no sets left" bonus under difficulty-weighted rewards.
- Exact XP rates and which personal stats to surface.

### Stage 2 — deferred, do NOT implement without explicit owner authorization
Multiplayer rooms/roles/room codes, realtime networking, backend/database/auth, server-authoritative scoring/claims, post-claim timers and cooldowns, reconnect handling, online rankings/leaderboards, match history, accounts, cloud save, and the advanced modes (Prism Contracts, Constellation Chain, Class Raid, Rival Duel, Ghost Board, quests, cosmetics). Do not add mock networking; local storage is not authoritative for competitive play.

### Known limitations
- No solo timer (intentional — timers are a Stage 2 host concept).
- Playwright covers Chromium only (desktop + mobile viewports).
- Google Fonts load from a CDN; offline falls back to system monospace (by design).

## 8. Guidance for the next LLM

- Read `CLAUDE.md` and `GAME_DESIGN_IMPROVEMENT.md` first; the repo is authoritative where they differ.
- Keep `src/domain/` pure. If a change needs React/DOM/storage, it belongs outside `domain/`.
- All scoring changes go through `ScoringConfig`; run `npm run simulate` and discuss the report with the owner before changing defaults.
- Keep EN/KO catalogs in parity — the build and tests enforce it.
- Add tests for every rule change; run `npm test`, `npm run build`, and `npm run test:e2e` before claiming done.
- Do not commit or push unless the owner explicitly asks.
